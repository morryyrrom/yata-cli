# ADR: ポリシーとフィクスチャの形式・配置・自動検出

> This Japanese version is the authoritative source. The English version (`ADR-0001-Policy-and-Fixture-Layout.md`) has not been written yet.

- ステータス: 承認
- 関連: [ADR: ポリシーエンジン](ADR-0001-Policy-Engine-Rego-with-Regorus.ja.md)、[ポリシー評価](../architecture/Architecture-Policy-Evaluation.ja.md)、[リソースモデル](../architecture/Architecture-Resource-Model.ja.md)、[テスト方針](../architecture/Architecture-Testing-Strategy.ja.md)

## 背景

ルール(ポリシー)を、どこに置き、どう配布し、どう見つけて読み込み、どう識別するかを決める必要があります。

要件は次のとおりです。

- 1 ルール 1 ファイルとし、中央の一覧に追記しなくても自動で読み込まれる
- ルールごとに、合格・不合格の両方のフィクスチャを持つ
- ルールの ID が、並列に追加されるルールの間で重複せず、リリースをまたいで変わらない
- ルールの追加・修正を、CLI のリリースを待たずに届けられる
- 利用者が独自のルールを同じ形式で使える
- ポリシーのリポジトリの中の階層は、ルールの作者が自由に決められる
- ルールのセットと CLI の組み合わせが合わないことを、実行時に検出できる

## 決定

### 配布と読み込み

- ルールは `yata` のバイナリにも、yata-cli のリポジトリ(どのクレートの中)にも含めない
- ルールは別のリポジトリ(ポリシーのリポジトリ)で配布する。利用者はそれを取得し、そのディレクトリ(ポリシーのディレクトリ)を `yata` に指定する
- `yata` は実行時にポリシーのディレクトリを走査してルールを見つける。ネットワークからポリシーを取得しない
- ポリシーのディレクトリの指定は `--policy-dir` → 環境変数 `YATA_POLICY_DIR` → 既定の場所の順(オプションがあれば環境変数は使わない)。既定の場所は未決事項で、決まるまでは指定が無ければ終了コード 2
- 走査と読み込み、マニフェストの検証は `yata-engine` が行う。ディレクトリの決定は `yata-cli` が行う

### ディレクトリの構成

```
<policy-dir>/
├── yata-policies.json                  # マニフェスト(ルールの一覧ではない)
├── lib/                                # 共通の関数のライブラリ
│   └── <name>.rego
└── <任意の階層>/
    ├── <rule>.rego                     # ルール 1 つ
    └── <rule>.fixtures/
        ├── pass_<case>.json
        └── fail_<case>.json
```

- 階層は自由。ルールのファイルは `<ルール名>.rego` で、`lib/` の下を除き、ルートの直下も含めて、任意の場所に置ける
- ディレクトリ名、ルール名、マニフェストの `name`、リソース種別の各部分は `[a-z][a-z0-9_]*` に限り、Rego の予約語(`as`、`contains`、`default`、`else`、`every`、`false`、`if`、`import`、`in`、`not`、`null`、`package`、`some`、`true`、`with`)を使わない。パッケージ名や `input.aws.<service>.<resource>` を、ドット区切りの形で必ず書けるようにするため。違反はルール単位の失敗(マニフェストの `name` はディレクトリ全体の失敗)
- メタデータもルールのファイルに書く(1 ルール 1 ファイル)
- ルールのプロバイダは、パスではなく、メタデータの `target_type` の最初の部分で決まる
- 深さは資源の上限(最大の深さ)だけで制限し、「浅すぎる・深すぎる」の検査はしない。最大の深さより深いディレクトリに中身があれば、ディレクトリ全体の失敗(終了コード 2)にする
- ルールの追加・変更で触るのは、そのルールのファイルとフィクスチャのディレクトリだけ

### ルール ID とパッケージ名

- ルール ID は `<マニフェストの name>.<ディレクトリ名>.….<ルール名>`(区切りは `.`)。例: `example_policies.s3.bucket_public_access_block`
- 各部分は `.` を含まない(`[a-z][a-z0-9_]*`)ので、`.` で区切っても曖昧にならない。`.` は Rego のパッケージ名の区切りと同じで、対応させやすい
- ポリシーのセットのバージョンは ID に含めない(バージョンは `ScanReport.policies` に出す)
- ID はメタデータに書かず、パスとマニフェストだけから決まる。ファイルの移動・改名で ID は変わる
- パッケージ名は `yata.rules.<ルール ID>`。違えば読み込みの失敗
- マニフェストの `name` がポリシーのディレクトリの間で重複したら、ディレクトリ全体の失敗(終了コード 2)。1 つのディレクトリの中ではパスが一意なので、ID は重複しない
- 連番は使わない(並列に追加したルールで同じ番号を使ってしまうため)

### ライブラリ

- ルートの `lib/` の下の `.rego` は、ルールではなく共通の関数のライブラリとする。パッケージ名は `yata.lib.<マニフェストの name>` で始める
- ライブラリは、同じポリシーのディレクトリのルールを評価するエンジンにだけ読み込む
- ライブラリの誤りはディレクトリ全体の失敗(全ルールに影響するため)
- ポリシーのリポジトリでの使い方: 1 ファイル 1 パッケージにして話題ごとにファイルを分ける、既存の関数の意味を変えずに足す形で直す、`lib/` の変更は単独の PR にする([ポリシー評価](../architecture/Architecture-Policy-Evaluation.ja.md) の「ライブラリ」)

### マニフェスト

- ポリシーのディレクトリのルートに `yata-policies.json` を置く。無ければ読み込みエラー(終了コード 2)
- 中身は `format_version`(ポリシーの形式のバージョン)、`name`(`[a-z][a-z0-9_]*`、予約語を除く。ID の先頭)、`version`(ポリシーのセットのバージョン)、`min_yata_version`(必要な `yata` の最低バージョン)。項目の詳細は [ポリシー評価](../architecture/Architecture-Policy-Evaluation.ja.md)
- ルールを列挙しない。中央の一覧ではなく、ルールの追加でマニフェストを書き換える必要は無い(新しいリソース種別を使うルールを足すときに `min_yata_version` を上げる場合を除く)
- `format_version` がその `yata` の対応する値でない、または実行中の `yata` が `min_yata_version` より古い場合は、終了コード 2 にする
- JSON にするのは、`yata` がすでに `serde_json` を使っており、TOML などのパーサーを追加しなくて済むため
- `min_yata_version` は `x.y.z` の形に限る(違えば終了コード 2)。比べるときは、実行中の `yata` のバージョンのプレリリースの部分を無視する
- マニフェスト、ルールのメタデータ、`fail` の要素の知らないキーは無視する(前方互換)。判定に関わらないキーを足すときは `min_yata_version` を上げなくてよく、そのキーの効果を必須にしたい場合だけ上げる。正しく評価するために必須のキーを足すときは `format_version` を上げる
- リソースの構成情報(`configuration`)は、公開した種別では項目の追加だけを許す。名前の変更・削除・型や意味の変更が必要なら、新しいリソース種別名を作る(原則)。`format_version` を上げるのは `input` 全体の形やリソースの共通の項目を変えるときだけ。種別名を変えるほうが、影響がその種別を使うルールだけに限られるため。例外として、秘密の値を伏せる項目の追加は、安全上の修正として同じ種別名のまま行い、リリースノートで告知する(その項目を参照するルールは影響を受けうる)([リソースモデル](../architecture/Architecture-Resource-Model.ja.md) の「構成情報の互換性」)
  - この例外は廃止した。コレクターは秘密の値も伏せずに入れる方針とし、伏せる規則をなくしたため([リソースモデル](../architecture/Architecture-Resource-Model.ja.md) の「コレクターの方針」「秘密の値の扱い」、[最初のルール群の範囲](../features/Feature-0005-Initial-Rule-Set-Scope.ja.md) の「コレクターの方針」)

### ルールの書式

- `metadata`(定数のオブジェクト)と `fail`(部分集合ルール)を持つ
- メタデータの `target_type`(検出の対象の種別 1 つ)と `related_types`(参照するだけの種別の配列、任意)で、使う種別を宣言する
- `fail` の各要素は `{resource_id, resource_region, message, path, actual, expected}`(`resource_region` と `path` 以降は任意)。不合格の箇所ごとに要素を返す
  - `resource_region` は、同じ `id` が複数のリージョンに現れる種別(CloudTrail の shadow trail など)で、そのうち 1 つのリソースを検出の対象にするときに付ける。省略すると、その `id` のすべてのリソースの検出になる([リソースモデル](../architecture/Architecture-Resource-Model.ja.md) の「id の一意性」、[最初のルール群の範囲](../features/Feature-0005-Initial-Rule-Set-Scope.ja.md) の「同じ ARN の証跡と `id`」)
- ルールは `input.aws.s3.bucket` のように、リソース種別を入れ子にした形で参照する
- 項目と規約は [ポリシー評価](../architecture/Architecture-Policy-Evaluation.ja.md) で定める

### フィクスチャの形式

図: [フィクスチャの期待値と結果の対応](../diagrams/Diagram-0011-Result-to-Resource-Mapping.md)

各フィクスチャは JSON で、ルールへの入力と期待する結果を持ちます。

```json
{
  "description": "Bucket with BlockPublicAcls disabled",
  "input": {
    "account": { "account": "aws-123456789012", "id": "123456789012", "provider": "aws" },
    "regions": ["us-east-1"],
    "aws": {
      "s3": {
        "bucket": [
          {
            "id": "arn:aws:s3:::example-bucket",
            "type": "aws.s3.bucket",
            "account": "aws-123456789012",
            "region": "us-east-1",
            "name": "example-bucket",
            "tags": {},
            "configuration": {
              "ListBuckets": { "Name": "example-bucket", "CreationDate": "2026-01-01T00:00:00Z" },
              "GetPublicAccessBlock": {
                "PublicAccessBlockConfiguration": {
                  "BlockPublicAcls": false,
                  "IgnorePublicAcls": true,
                  "BlockPublicPolicy": true,
                  "RestrictPublicBuckets": true
                }
              }
            }
          }
        ]
      }
    }
  },
  "expected": {
    "fail": ["arn:aws:s3:::example-bucket"]
  }
}
```

- `input` は、エンジンがそのルールに渡す `input` と同じ形([リソースモデル](../architecture/Architecture-Resource-Model.ja.md) の「ポリシーエンジンへの渡し方」)
  - ルールが `target_type` / `related_types` で宣言した種別の配列をすべて置く(0 件のケースは空の配列)。欠けたフィクスチャは形式の誤りとしてテストを失敗させる(実際の評価では、未収集の種別があるとルールは `skipped` になり評価されないため)
- `expected.fail` は不合格になるリソースの一覧(順不同)。ここに無い、`target_type` のリソースは合格になることを期待する。各要素は次のどちらかで書く
  - `id` の文字列(例: `"arn:aws:s3:::example-bucket"`): その `id` のすべてのリソース(リージョンを問わない)が不合格になることを期待する。`id` が一意な種別では、これまでどおりこの形で書けばよい
  - `{"id": ..., "region": ...}` のオブジェクト(例: `{"id": "arn:aws:cloudtrail:us-east-1:123456789012:trail/example-trail", "region": "eu-west-1"}`): その `id` とリージョンのリソースだけが不合格になることを期待する。同じ `id` が複数のリージョンに現れる種別で、どのリージョンのものが不合格かを確かめるときに使う。`id` と `region` はどちらも必須で、文字列
  - 重複なし: 同じ `id` の文字列を重ねること、同じ `{id, region}` を重ねること、同じ `id` を文字列とオブジェクトの両方で書くことは、フィクスチャの誤り
  - 各要素は `input` の `target_type` のリソースを 1 つ以上指す。指さない要素(`id` の書き間違いなど)はフィクスチャの誤り
  - 比べ方は [ポリシー評価](../architecture/Architecture-Policy-Evaluation.ja.md) の「期待値の比べ方」
- `input` の同じ種別の配列に、`id` と `region` の組が同じリソースを複数置くことは、フィクスチャの誤り([リソースモデル](../architecture/Architecture-Resource-Model.ja.md) の「id の一意性」)
- ファイル名は `pass_` または `fail_` で始める
  - `pass_`: `expected.fail` が空であること
  - `fail_`: `expected.fail` が 1 件以上であること
- 各ルールに `pass_` と `fail_` を 1 つ以上ずつ置く。境界のケースは追加のファイルにする
- 値はダミーだけを使う
- 構成情報に取得の失敗の印(`{"yata_error": {"kind": ..., "message": ...}}`)を含めてよい。そのケースのフィクスチャを用意し、ルールが印をどう扱うか(印のリソースを `fail` にしない、または明示的に判定する)を確かめるとよい。フィクスチャの期待値は `expected.fail` だけで比べ、状態(`incomplete`)は比べない
- 印の形は [リソースモデル](../architecture/Architecture-Resource-Model.ja.md) の「操作ごとの取得の失敗」

### 自動検出(実行時の走査)

図: [ポリシーの読み込みの流れ](../diagrams/Diagram-0001-Policy-Loading.md)

- `yata-engine` がポリシーのディレクトリの下を、最大の深さまで再帰的に走査し、`.rego` を見つける。`lib/` の下はライブラリ、それ以外はルール
- `.` で始まるディレクトリは走査しない
- 指定した最上位のディレクトリはシンボリックリンクでもたどるが、その下のシンボリックリンクと reparse point(Windows の junction など)はディレクトリ・ファイルともにたどらず、見つけたら失敗にする(ルールのファイル・そのフィクスチャのディレクトリの中なら `rules test` で 1・それ以外のコマンドで 2、それ以外の場所とマニフェストならどのコマンドでも 2)。詳細は [ポリシー評価](../architecture/Architecture-Policy-Evaluation.ja.md) の「外部のポリシーの安全性」
- 見つけたルールは ID の順に並べる
- 複数のポリシーのディレクトリを指定した場合は、それぞれにマニフェストが必要で、ディレクトリごとに 1 つずつ検証する
- 失敗の種類ごとの終了コード(`yata rules test` とそれ以外のコマンドの違い)は [ポリシー評価](../architecture/Architecture-Policy-Evaluation.ja.md) の「失敗の種類と終了コード」で定める
- フィクスチャは `yata rules test` のときだけ読む(`yata scan` では読まない)
- 中央の一覧ファイルは存在しない

### ポリシーのリポジトリでの確認

`yata` は、ポリシーのリポジトリが CI でルールを確かめるための仕組みとして `yata rules test --policy-dir <DIR>` を提供します。

- 次をまとめて行う: マニフェストの検証、読み込みの検証(ライブラリ、構文、パッケージ名とパスの一致、メタデータ、名前の規則)、フィクスチャのそろい方と形式、ダミー値の確認、フィクスチャの実行、ルールの種別がその `yata` のプロバイダで対応しているかの確認
- ポリシーのリポジトリの CI は、マニフェストの `min_yata_version` 以上の `yata` で `yata rules test --policy-dir .` を実行する
- 詳細と終了コードは [ポリシー評価](../architecture/Architecture-Policy-Evaluation.ja.md) と [CLI インターフェース](../architecture/Architecture-CLI-Interface.ja.md)
- ポリシーのリポジトリ自体の構成(CI の定義、リリースの方法など)は、この ADR の範囲外とする

## 検討した選択肢

### 配布の方法

| 選択肢 | 判断 |
| --- | --- |
| 外部のリポジトリだけで配布し、実行時に読み込む(採用) | ルールの追加・修正を CLI と独立にリリースできる。利用者がルールのセットのバージョンを選んだり、自分で手を加えたりしやすい。yata-cli のリポジトリはコードだけになり、ルールの追加でこのリポジトリのブランチが衝突しない。代わりに、取得の手間と、CLI との互換性の確認(マニフェスト)が必要になる |
| バイナリに同梱する(build.rs で埋め込む) | インストールだけで使え、互換性の問題も起きない。ただしルールの修正のたびに CLI のリリースが要り、ルールとコードが同じリポジトリで混ざる |
| 同梱し、外部のルールも追加で読めるようにする(両方) | 両方の長所を持つが、同梱分と外部分の ID の重複、どちらの版が優先されるか、同梱分の古さなど、扱う状態が増える。読み込みの経路が 2 つになり、テストも 2 通り必要になる |

### 配置と検出

| 選択肢 | 判断 |
| --- | --- |
| 自由な階層 + `<ルール名>.rego` + 実行時の走査(採用) | ルールの作者が分類を自由に決められる。ルールの追加がファイルの追加だけで済み、衝突しない。依存クレートも増えない |
| 1 ルール 1 ディレクトリ(`<provider>/<service>/<rule>/policy.rego`)の固定の階層 | 構成は分かりやすいが、分類の自由が無く、ファイル名がすべて `policy.rego` でエディタ上で区別しにくい |
| ルールを 1 つのファイルに複数書く(サービスごとなど) | 同じサービスのルールを並列に追加すると衝突する |
| ルールの一覧ファイル(`rules.toml` など)に登録 | ルールの追加のたびに同じファイルに追記し、衝突する |
| メタデータを別ファイル(`metadata.yaml` など)にする | 1 ルールのファイルが 2 つに分かれ、整合性の確認が要る。YAML のパーサーも必要になる。Rego のオブジェクトで十分に書ける |
| OPA の METADATA 注釈(コメント)でメタデータを書く | OPA との互換性は高いが、regorus での注釈の取り出しに依存する。定数のオブジェクトの方がエンジンから確実に取り出せる |
| フィクスチャを Rego のテスト(`test_` ルール)で書く | `opa test` と同じ書き方になるが、入力の JSON がルールのファイルに混ざって長くなり、Rego を知らない人がケースを足しにくい。期待値の確認も一律にしにくい |
| フィクスチャを `<dir>/<ルール名>/` に置く | ディレクトリ名がルール名と同じになり、その下に別のルールを置いた場合と区別できない。`<ルール名>.fixtures/` なら名前の規則(`[a-z][a-z0-9_]*`)に当てはまらないので、名前空間のディレクトリと混ざらない |
| ライブラリを `_` で始まるファイルにする | 階層のどこにでも置けるが、どのルールから使われるかが分かりにくい。`lib/` にまとめる方が見つけやすく、規則も 1 つで済む |

### ルール ID

| 選択肢 | 判断 |
| --- | --- |
| `<name>.<ディレクトリ>.<ルール名>`(採用) | パスから一意に決まり、メタデータとの不一致が起きない。リリースをまたいで変わらない |
| `<name>-<version>(-<サブディレクトリ>)-<ルール名>` | バージョンを含めると、リリースのたびに全ルールの ID が変わり、`--rule` の指定、抑制、SARIF のアラートの追跡、結果の比較が壊れる。区切りの `-` は、名前に `-` があると曖昧になる |
| メタデータに ID を書く(パスと独立) | 移動しても ID が変わらないが、ポリシーのセットの中で ID の一意性を別に確かめる必要があり、パスとの対応も分かりにくくなる |
| 連番のルール ID(`YATA-AWS-001` など) | 並列に追加したルールで同じ番号を使ってしまう |

### 互換性の確認

| 選択肢 | 判断 |
| --- | --- |
| ルートのマニフェストに形式のバージョンと必要な `yata` の最低バージョンを書く(採用) | 読み込みの最初に 1 回確かめるだけで済む。ルールを列挙しないので中央の一覧にならない |
| ルールごとのメタデータに対応する `yata` のバージョンを書く | ルールごとに確かめられるが、全ルールに同じ情報を重複して書くことになり、更新の漏れが起きやすい |
| 確認しない | 古い `yata` で新しい形式のルールを読むと、読み込みエラーや誤った判定になり、原因が分かりにくい |
| マニフェストに `yata` のバージョンの範囲(上限を含む)を書く | 上限は「この `yata` が読める形式か」で決まるため、`format_version` で表せる。範囲の比較のためのクレート(`semver` など)も不要にできる |

## 結果

- ルールの追加は、ポリシーのリポジトリに `.rego` ファイル 1 つとフィクスチャのディレクトリを足すだけで完結する
- yata-cli のリポジトリには、ルールの本体は置かない。テストには最小のポリシーのセットだけを置く([テスト方針](../architecture/Architecture-Testing-Strategy.ja.md))
- 利用者は、`yata` に加えてポリシーのリポジトリを取得し、場所を指定する必要がある。案内は利用者ガイドで行う
- 新しいリソース種別を使うルールは、その種別に対応した `yata` のリリースの後に公開し、マニフェストの `min_yata_version` を上げる
- ルール ID はパスから決まるため、ファイルの移動・改名で変わる。利用者の設定(`--rule` の指定など)や過去の結果との比較に影響するため、ポリシーのリポジトリでは移動・改名を避け、行う場合は互換性の無い変更として告知する
- 利用者が用意したファイルを読むため、評価は時間の上限とネットワークを使わない設定で行う([ADR: ポリシーエンジン](ADR-0001-Policy-Engine-Rego-with-Regorus.ja.md))。信頼の前提、資源の上限、出力への注入、パスの扱い、組み込み関数の扱いは [ポリシー評価](../architecture/Architecture-Policy-Evaluation.ja.md) の「外部のポリシーの安全性」で定める。`yata` はポリシーの署名や出所を検証しないため、利用者が信頼できる出所から取得したポリシーを使う前提になる
- ポリシーと `yata` が別々にリリースされるため、コレクターの構成情報を変えると外部のルールが黙って `pass` になりうる。公開した種別の構成情報は追加だけを許し、互換性の無い変更は新しいリソース種別名で行う。このリポジトリでは、コレクターの出力を固定するテストで確かめる。秘密の値を伏せる項目の追加の例外は、伏せる規則をなくしたため廃止した(上の「マニフェスト」)
- 同じ `id` が複数のリージョンに現れる種別は、`fail` の要素の `resource_region` と、`expected.fail` の要素のオブジェクトの形(`{"id", "region"}`)で、1 つのリソースを指す。どちらも省略・文字列の形で書けるため、`id` が一意な種別のルールとフィクスチャは書き方が変わらない
  - `resource_region`(無視すると判定が変わるキー)、`expected.fail` のオブジェクトの形、`id` の一意性の変更(リソースの共通の項目の意味の変更)は、どれも本来は `format_version` を上げる対象だが、ポリシーの形式の最初のリリースの前に定めるため、`format_version` `1` に含める
