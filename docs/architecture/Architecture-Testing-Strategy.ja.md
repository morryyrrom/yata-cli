# テスト方針

> This Japanese version is the authoritative source. The English version (`Architecture-Testing-Strategy.md`) has not been written yet.

テストの種類と、実 AWS に接続しないための対策を定めます。入口は [アーキテクチャ概要](Architecture-Overview.ja.md) です。

## 原則

- テストは実 AWS に接続しない。フィクスチャとモックだけを使う
- フィクスチャ・テストデータの値はダミーだけを使う。アカウント ID は `123456789012` など AWS のドキュメントで例に使われる値にする
- テストは他の worktree と状態を共有しない。ファイルを書くテストは `tempfile` の一時ディレクトリを使う
- テストはネットワークに接続しない(依存のダウンロードを除く)
- `cargo test --workspace` だけで全テストが走るようにする。追加のツールやサービスを必要としない

## テストの種類

| 種類 | 対象 | 置き場所 | 方法 |
| --- | --- | --- | --- |
| 単体テスト | 各クレートの関数・型 | 各ファイルの `#[cfg(test)] mod tests` | 通常の Rust のテスト |
| ポリシーの読み込みのテスト | `yata-engine` の走査・マニフェスト・検証 | `yata-engine/tests/` | テスト用の最小のポリシーのセットを読み込む(下記) |
| ルールのテストの機能のテスト | `yata-engine` の `testing` モジュール(静的検査を含む) | `yata-engine/tests/` | テスト用のポリシーのセットで、成功・失敗の両方を確かめる(下記) |
| コレクターのテスト | 各コレクター | コレクターのファイル内 | `aws-smithy-mocks` で SDK の応答をモックする(下記) |
| 読み取り専用のテスト | `yata-provider-aws` 全体 | `yata-provider-aws/tests/` | [AWS アクセス](Architecture-AWS-Access.ja.md) の「読み取り専用の強制」のテスト |
| 出力のテスト | 各出力形式 | `yata-report/tests/` | 決まった `ScanReport` から作った出力を、期待するファイルと比べる(下記) |
| スナップショットのテスト | 書き込み・読み込み・検証 | `yata-core/tests/`、`yata-cli/tests/` | 一時ディレクトリに書き、読み戻して一致を確かめる。壊れたスナップショットで終了コード 2 になることを確かめる(下記) |
| CLI の統合テスト | `yata` バイナリ | `yata-cli/tests/` | `assert_cmd` でバイナリを実行する。スキャンは `--snapshot` だけを使い、ポリシーはテスト用のセットだけを使う |
| 対応の検査 | ルールの `target_type` / `related_types` とプロバイダ | `yata-cli` の単体テストと統合テスト | 対応していない種別を宣言したルールで終了コード 2 になることを確かめる |
| オプションの優先度のテスト | オプション > 環境変数 > 既定値 | `yata-cli` の単体テストと統合テスト | オプションと環境変数の両方を指定したときにオプションだけが使われること(混ぜないこと)を確かめる |

### テスト用のポリシーのセット

ルールの本体は別のリポジトリにあり、このリポジトリには置きません。このリポジトリのテストは、実際のポリシーのリポジトリに依存せず、テスト用の最小のポリシーのセットだけを使います。

- `crates/yata-engine/tests/fixtures/policies/<case>/`: 読み込みとルールのテストの機能を確かめるためのセット
  - `valid/`: マニフェスト、ライブラリ(`lib/`)、ルートの直下と複数の階層に置いた少数のルール(`<ルール名>.fixtures/` のフィクスチャ付き。失敗の印を含むフィクスチャも置く)
  - 失敗のケース: マニフェストが無い、`format_version` が対応外、`min_yata_version` が新しすぎる・`x.y.z` でない、マニフェストの `name` の重複・予約語、パッケージ名とパスの不一致、名前の文字の規則に合わない名前(数字で始まる、予約語)、`related_types` にほかのプロバイダの種別、ライブラリの誤り、Rego の構文エラー、`fail` の要素の形の誤り、対応するルールの無い `.fixtures`、フィクスチャのそろい方の不足、ダミー以外のアカウント ID、期待と違う結果、シンボリックリンク、深さの上限、など。1 ケース 1 ディレクトリにする(シンボリックリンクのケースはリポジトリに置かず、テストの中で一時ディレクトリに作る)
- `crates/yata-cli/tests/fixtures/policies/`: CLI の統合テスト用のセット
  - ルールの `target_type` には、コレクターに依存しない `aws.account.account` を使う。コレクターの追加・変更で CLI のテストが壊れないようにするため
  - 対応していない種別(例: `aws.example.unsupported`)を宣言したルールを持つセットも用意し、終了コード 2 を確かめる
- `crates/yata-cli/tests/fixtures/snapshots/<case>/`: CLI の統合テスト用のスナップショット(マニフェストと ResourceSet のファイル。ダミー値のみ)
  - 正しいもの、一部の組が失敗したもの(終了コード 4)、未収集の種別があるもの(`not_collected`)、構成情報に失敗の印を持つリソースがあるもの(`incomplete` と `incomplete_resources`、終了コード 4)、マニフェストと中身が一致しないもの(終了コード 2)など
- テスト用のルールは、読み込みと評価の仕組みを確かめるためのもので、実際のチェック(CIS のコントロールなど)を実装しない
- フィクスチャの書式と期待値の書き方は [ADR: ポリシーとフィクスチャの形式・配置・自動検出](../adr/ADR-0001-Policy-and-Fixture-Layout.ja.md) を参照

### ルールのテストの機能のテスト

`yata rules test` の検査(マニフェスト、読み込みの検証、フィクスチャのそろい方、ダミー値、フィクスチャの実行、プロバイダの対応)と、終了コード(ルール単位の失敗は 1、ディレクトリ全体の失敗は 2)が、正しいセットでは成功し、各失敗のケースでは失敗として報告されることを確かめます。実際のルールのテストは、ポリシーのリポジトリの CI で `yata rules test --policy-dir .` を実行して行います([ポリシー評価](Architecture-Policy-Evaluation.ja.md))。

### コレクターのテスト

- `aws-smithy-mocks` の `mock!` / `mock_client!` で SDK の操作ごとに応答を定義し、コレクターが作る `Resource` を確かめる
- 確かめること: 構成情報の変換(API の操作名ごとの格納、項目名、値の変換の規則)、ページングで全件を取ること、値が無い場合の `null`、「設定が存在しない」エラーで `null` になること、リソースを列挙する操作の `AccessDenied` などのエラーが `CollectError` になること、リソースごとの付随情報を取る操作のエラーが構成情報の失敗の印(`yata_error`)になり組は成功のままになること
- 秘密の値が `"<redacted>"` に伏せられていることを確かめる(伏せる項目には、モックの応答でダミーの値を入れておく)
- モックを使うには、SDK のサービスのクレートの `test-util` 機能が必要。`[dev-dependencies]` で有効にする
- 実際のクライアントの生成(認証情報の解決)は通らないようにする
- コレクターが作る `Resource` の JSON を、期待するファイル(コレクターごと)と比べて出力を固定する。構成情報の項目の名前の変更・削除・型の変更は、外部のルールを黙って `pass` にするため、このテストで検出する([リソースモデル](Architecture-Resource-Model.ja.md) の「構成情報の互換性」)
  - 期待するファイルの更新は、出力のテストと同じく環境変数を付けたときだけ行う。更新の差分が項目の追加以外を含む場合は、互換性の無い変更として扱い、新しいリソース種別名にする
  - AWS SDK を更新する PR では、このテストの結果を必ず確かめる

### スナップショットのテスト

- `Inventory` を一時ディレクトリに書き、読み戻して一致することを確かめる
- 出力先がすでにある場合(`--overwrite` なし)、`--overwrite` の対象がスナップショットでない場合に、終了コード 2 で既存のディレクトリが変わらないことを確かめる
- 書き込みの途中の失敗を模したときに、一時ディレクトリが残らず、既存の出力先が変わらないことを確かめる
- Unix で、ディレクトリとファイルのアクセス権が `0700` / `0600` であることを確かめる
- 読み込みの検証(マニフェストと中身の不一致、マニフェストに無いファイル、組の過不足、シンボリックリンク、上限)で終了コード 2 になることを確かめる

### 出力のテスト

- 決まった `ScanReport`(ダミー値)から各形式の出力を作り、`yata-report/tests/golden/` の期待するファイルと比べる
- 期待するファイルの更新は、環境変数(例: `YATA_UPDATE_GOLDEN=1`)を付けてテストを実行したときだけ行う
- 日時など実行のたびに変わる値は、テスト用に固定した値を `ScanReport` に入れる

### CLI の統合テスト

- `yata scan --policy-dir <テスト用のセット> --snapshot <テスト用のスナップショット>` で、終了コードと出力(`path` / `actual` / `expected` を含む)を確かめる。`--omit-values` で `actual` / `expected` が省かれることも確かめる
- `yata rules list`、`yata rules test`、`yata permissions` も同様に確かめる
- 引数の誤り、同時に指定できないオプション(`--snapshot` と `--profile` など)、スナップショットの検証の誤り、ポリシーのディレクトリの指定が無い・見つからない、マニフェストが合わない、対応していない種別(いずれも終了コード 2)を確かめる
- `--policy-dir` と `YATA_POLICY_DIR`、`-v` / `-q` と `YATA_LOG` の優先度(オプションがあれば環境変数を使わない)を確かめる

## 実 AWS に接続しないための対策

- テストで AWS に接続しうるコード(認証情報の解決、実クライアントの生成)を通さない構成にする
  - コレクターはモックのクライアントで、CLI はスナップショットでテストする。`yata collect` の統合テストは行わず、スナップショットの書き込みは `Inventory` を直接渡す単体テストで確かめる
- CLI の統合テストでは、子プロセスの環境変数を次のように設定し、誤って利用者の設定や認証情報を読まないようにする
  - `AWS_CONFIG_FILE`、`AWS_SHARED_CREDENTIALS_FILE` を一時ディレクトリ内の存在しないパスにする
  - `AWS_ACCESS_KEY_ID`、`AWS_SECRET_ACCESS_KEY`、`AWS_SESSION_TOKEN`、`AWS_PROFILE` を消す
  - `AWS_EC2_METADATA_DISABLED=true` にする
  - `YATA_POLICY_DIR` と `YATA_LOG` を消す(利用者の環境のポリシーや設定を読まないようにするため。優先度のテストでは、テスト用の値を明示的に設定する)
- `cargo run` や `aws` CLI による実環境での確認は、テストではなく手動の確認として扱い、実行前にメンテナーの確認を取る

## CI

CI では次を実行します(CI の作成は骨組みの Issue で行う)。

- `cargo fmt --all -- --check`
- `cargo clippy --workspace --all-targets -- -D warnings`
- `cargo test --workspace`
